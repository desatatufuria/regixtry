# Exploration: Global + per-repository config overrides (Trivy, gitleaks, future image-signing)

## Goal

Add a generic global-plus-per-repository override mechanism for scan-feature configuration (Trivy, gitleaks now; image-signing later — no code yet). Mirrors Harbor's system-allowlist + per-project-override pattern, explicitly scoped to admin/security config (no per-user scoping — ruled out as not an industry pattern). Gitleaks must NOT regain a schedule/interval concept (deliberately rejected this session: immutable-content scans never need periodic rescan). Gitleaks' primary override is a native `.gitleaks.toml` path (industry-standard, confirmed via gitleaks docs); Trivy's override needs differ because Trivy is CVE-severity-based, not secret-based (confirmed via Trivy CLI docs: `--ignorefile` for `.trivyignore`, `--ignore-policy` for a Rego policy file — distinct mechanism from `--severity`).

## Current State

**No per-repository settings precedent exists anywhere.** `domain.RepositoryRef` (`internal/domain/regixtry/repository.go:10`) is a bare `{Name string}` — no config fields, no foreign settings table joins it. `ports.MetadataStore` (`internal/ports/regixtry.go:22-55`) has zero repository-scoped settings methods; `Catalog` (`store.go:319`) only lists names. This change introduces the first per-repository config concept in the codebase.

**Global `ScanSettings` resolution path** (single row per tenant+feature, established this session's predecessor work): `loadFeatureSettings` (`internal/app/regixtry/feature_registry.go:237`) calls `metadata.GetScanSettings(ctx, tenant, feature)`; `NotFound` → returns in-code defaults with a `configured=false` flag, never errors. This "row-presence-boundary" pattern (row exists → use it in full; row absent → full code-default struct) is the exact precedent to reuse for per-repo overrides, not a field-by-field sparse merge. `mergeFeatureSettings` (`feature_registry.go:258`) does apply a sparse merge, but only for `ConfigureFeature`'s input DTO onto the single global row — it does not establish sparse merging across a global/override *boundary*.

**Resolution point that must grow to check for a repo-level override**: `executeScanRun` (`service_scanning.go:295`) receives `settings ports.ScanSettings` already resolved by its caller (`queueScheduledScan`/`queuePushScan`) and passes it straight to `scanTarget`/`scanRunner.Run`; `executeSecretScanLeg` (`service_scanning.go:346`, gitleaks) runs alongside in its own goroutine from the same trigger. Neither knows the repository at settings-resolution time today — the override lookup must happen where these callers currently fetch the single global row, keyed additionally by `run.Repository`.

**`gitleaks/runner.go` (`internal/infra/scanning/gitleaks/runner.go:45`)** has a fixed argv today — no `--config` flag support exists in the runner at all (grep for `ConfigPath`/`--config` returns nothing). Wiring a per-repo `.gitleaks.toml` path is new plumbing through `Runner.Run`, not a rename of an existing field.

**`ScanPolicySettings` scope tension**: `scan-policy-gate`'s proposal (`openspec/changes/scan-policy-gate/proposal.md` "Out of Scope") deliberately kept the vulnerability *pull-gate* threshold single-global-row, explicitly citing "matching existing `ScanSettings` granularity" as the justification. That justification is now stale — `ScanSettings` is about to gain per-repo granularity, but `ScanPolicySettings` should almost certainly stay global-only regardless (it's a pull-time admission gate, not a scan execution knob; per-repo policy variation is a materially bigger, separate product decision Harbor itself keeps distinct from per-project allowlists in UI terms). **Real, deeper coupling risk found**: a per-repo Trivy override's `--ignorefile`/`--ignore-policy` changes what Trivy *counts* as Critical/High findings for that repository's `ScanRun`, and `GetScanPolicySettings`'s global gate reads exactly those counts (`service_scanning.go:56-62`, `scanPolicyViolated`). So even though storage stays separate, a per-repo Trivy config override can silently change pull-gate outcomes for that repo. Not a naming collision — a real behavioral coupling `sdd-propose`/`sdd-design` must document, not silently ignore.

**TUI navigation precedent**: the closest existing "operate on one specific repository" entry point is `adminScanHistoryModal`, opened by `Enter` while a row is highlighted in the Repository Alerts tab (`model.go:1227-1243`, `m.adminView.TrivySelectedAlert` indexes `TrivySummaries`, binds `Repository: summary.Repository`). Global config modals (`trivyConfigModal` via `c` on the Runtime tab, `scanPolicyModal` via `p` on either Trivy tab) live at the feature-page level, not per-row. The least-disruptive entry point for "configure this repo's override" is a new keybinding (e.g. `o`) on a highlighted Repository Alerts row, opening a new modal bound to `summary.Repository` — structurally identical to how `ScanHistoryModal` already opens, not a new UX pattern. All admin TUI modals follow the same 3-piece shape: state struct + `Active() bool` in `session.go`, key routing in `model.go` (dispatched via a chain of `Active()` checks around `model.go:1064`), renderer in `admin_views.go`, composited via `compositeOverlay` (`admin_overlay.go:63`). A new modal follows this exactly but adds one more `Active()` branch to an already-long dispatch chain.

## Affected Areas

- `internal/ports/regixtry.go` — new override type(s) + `MetadataStore` methods (get/upsert/clear override for tenant+repository+feature).
- `internal/infra/metadata/sqlite/store.go` — new table(s); the codebase's established idiom is explicit typed columns + additive `ALTER TABLE ADD COLUMN` (as used for `scan_settings`/`scan_policy_settings`), not JSON blobs — no JSON-column precedent exists anywhere in this store.
- `internal/app/regixtry/feature_registry.go` / `service_scanning.go` — the settings-resolution point (`loadFeatureSettings` callers, `queueScheduledScan`/`queuePushScan` → `executeScanRun`) must check for a repo-level override before falling back to the existing global row.
- `internal/infra/scanning/gitleaks/runner.go` — new `--config` plumbing (does not exist today).
- `internal/infra/scanning/trivy/runner.go` — new `--ignorefile`/`--ignore-policy` plumbing.
- `internal/tui/session.go`, `model.go`, `admin_views.go`, `admin_tables.go` — new per-repo override modal off the Repository Alerts row, new admin HTTP client calls.
- `internal/protocol/http/admin_handlers.go`, `router.go` — new GET/PUT(or PATCH)/DELETE routes scoped by repository.

## Approaches Considered

**Storage shape**:

1. **EAV table** — `repository_feature_config_overrides(tenant, repository, feature_name, field_key, field_value)`. Pros: literally zero schema change for image-signing. Cons: loses Go's established type-safety norm (every existing settings type — `ScanSettings`, `ScanPolicySettings`, `FeatureConfigureInput` — is a typed struct, never a map); `Timeout time.Duration`/`MaxConcurrency int` become strings needing ad hoc per-field parse/validate duplicated from `normalizeScanSettings`; no compile-time guarantee on resolved values. Effort: Medium, Risk: High (type-safety regression, no precedent).

2. **Per-feature typed tables** — `repository_trivy_overrides`, `repository_gitleaks_overrides`, (later) `repository_signing_overrides`. Pros: matches the codebase's existing typed-column/`ALTER TABLE ADD COLUMN` idiom exactly; simplest resolution query (`SELECT ... WHERE tenant=? AND repository=?` → `NotFound` → global fallback, identical shape to today's `loadFeatureSettings`). Cons: **directly conflicts with the explicit requirement** that the storage/resolution shape "should not be gitleaks/trivy-specific" — image-signing would need its own new migration + new interface methods when it lands, not reuse. Effort: Low, Risk: Low technically but fails the stated reuse constraint.

3. **Single generic table, typed JSON payload per feature** — `repository_feature_overrides(tenant, repository, feature_name, payload, updated_at)` where `payload` is a JSON blob the Go layer marshals/unmarshals into a feature-specific typed struct (`TrivyOverrideFields{Enabled, IgnoreFilePath, IgnorePolicyPath, ...}`, `GitleaksOverrideFields{Enabled, ConfigPath, ...}`). One table serves any future feature (image-signing needs zero migration); Go-side type safety preserved via marshal/unmarshal at the boundary, same way `admin_handlers.go` decodes typed request bodies today. Cons: introduces a JSON-in-SQLite column, a genuinely new pattern for this store (no existing precedent); loses per-field SQL queryability; the established `ALTER TABLE ADD COLUMN` additive-migration idiom doesn't apply to an opaque blob — schema changes move into Go struct versioning instead. Effort: Medium, Risk: Medium (new pattern, but contained).

## Recommendation

**Approach 3** (generic table, typed JSON payload). It is the only option that satisfies the explicit reuse requirement ("not gitleaks/trivy-specific in storage/resolution shape") without sacrificing Go's established type-safety convention at the application boundary — approach 1 fails type-safety, approach 2 fails the reuse requirement outright. The resolution function stays feature-agnostic: `GetRepositoryOverride(tenant, repository, feature) → (payload []byte, found bool, err)`, and each feature module (trivy, gitleaks, later signing) owns its own typed marshal/unmarshal, mirroring how `normalizeScanSettings` already owns `ScanSettings` normalization today. Flag the new JSON-column pattern explicitly in the proposal so `sdd-design` documents it as a deliberate, scoped exception to the additive-column idiom, not an accidental drift.

## Risks

- Per-repo Trivy override (`--ignorefile`/`--ignore-policy`) changes finding counts that the *global* `ScanPolicySettings` pull-gate reads — a storage-level separation that is not a behavioral separation; must be documented, not silently assumed independent.
- `gitleaks/runner.go` and `trivy/runner.go` both need new argv plumbing (`--config`, `--ignorefile`/`--ignore-policy`) that does not exist today — this is new runner surface, not a rename.
- JSON-payload column is a new pattern in a codebase whose settings tables are 100% typed columns today; risks inconsistent conventions if not explicitly documented as scoped/deliberate.
- TUI modal dispatch chain (`model.go` `Active()` checks) is already long (`trivyConfigModal`, `scanPolicyModal`, `adminScanHistoryModal`, confirm modal, etc.); a new per-repo override modal adds one more branch — keep it, per precedent, as its own small modal rather than extending an existing one (mirrors `scanPolicyModal`'s explicit "sibling, not extension" decision).
- `ScanPolicySettings`'s existing "matches `ScanSettings` granularity" justification for staying global-only becomes stale once `ScanSettings` itself gains per-repo granularity — `sdd-propose` must state explicitly that policy-gate scope is unchanged by this work, not silently drift.

## Open Questions Requiring a Product Decision

1. **Override granularity**: full-row-replace (row exists → all its typed fields apply, mirrors `loadFeatureSettings`'s `configured` boolean and Harbor's real per-project mechanic — Harbor's "Copy From System" is a manual one-time seed action, not automatic ongoing field-level merge with the system list) vs. sparse per-field override. **Recommend full-row-replace** for simplicity and Harbor-precedent alignment, but this is a product decision, not decided here.
2. **Exact Trivy override field set**: `Enabled`, `IgnoreFilePath` (`.trivyignore`), `IgnorePolicyPath` (Rego), and possibly `Timeout`/`MaxConcurrency`? Does per-repo Trivy override need its own severity knob, or is severity intentionally left to the (global-only) `ScanPolicySettings` gate? Needs explicit product confirmation given the coupling risk noted above.
3. **Exact gitleaks override field set**: `Enabled` + `ConfigPath` (`.gitleaks.toml`) only, or also `Timeout`/`MaxConcurrency`?
4. **TUI entry-point placement**: new keybinding on a Repository Alerts row (recommended, follows `ScanHistoryModal` precedent exactly) vs. some other location — needs explicit confirmation before `sdd-design`.
5. **Clear-override HTTP semantics**: `DELETE` on the override resource (revert to global) vs. `PUT` with an explicit "use global" sentinel — `DELETE` is more RESTfully explicit and matches the row-presence-boundary resolution model recommended above.

## Ready for Proposal

Yes, contingent on the five open questions above being resolved (or explicitly deferred as flagged decisions) before `sdd-propose` — this mirrors how `scan-policy-gate`'s own three open questions were resolved between explore and propose rather than re-derived.
